# Account security backend implementation report

Completed 2026-10-06 (Asia/Shanghai). Scope: F01/F12, Task 1 of the account-security/rebinding plan.

## Delivered behavior

- New API-created accounts and administrator/CLI password resets require a first password change. CLI-created Operator/ReadOnly accounts also require a change; CLI bootstrap Admin accounts and pre-migration accounts retain access.
- Required-change sessions can only read auth me/CSRF/security status, verify MFA, change their password, or log out. The MFA exception lets an expired proof be renewed before the mandatory password change without removing that requirement. The gate runs after cookie authentication and before role authorization so expired cookies retain 401 and restricted valid sessions receive `PASSWORD_CHANGE_REQUIRED` consistently.
- Password changes validate the old password and Identity strength, reject reuse, clear the required-change flag, rotate the security stamp, refresh the current cookie, and invalidate other cookies. The existing eight-hour absolute cookie lifetime survives refreshes.
- Opt-in standard SHA1/six-digit/30-second TOTP accepts adjacent steps and records the greatest accepted step. Active and five-minute pending secrets use Data Protection; recovery codes contain 128 random bits and only SHA256 digests persist.
- Password-only MFA login returns a protected five-minute challenge. Its account ID, security stamp, expiry and active ID are checked in the account transaction. Completing a challenge consumes it; starting another password login replaces the earlier challenge for that account.
- TOTP and recovery consumption, failure counters, password/security changes and admin/CLI account changes share the existing PostgreSQL advisory account lock. Failed verification commits lockout accounting. Correct first-factor passwords do not erase MFA failures.
- MFA setup confirmation, disable and recovery regeneration follow the spec's proof requirements. Security operations and login have IP admission. Five-minute proof is retained in protected cookie properties and enforced before business writes; precise license search remains exempt.
- Audits store action/identity metadata only. No password, authenticator secret, challenge or recovery-code plaintext is recorded.

## Integration notes

- Fetch CSRF after password/MFA enable/disable success. Challenge login removes any previous complete application cookie, so refresh CSRF before challenge submission if a previous authenticated session existed.
- `TWO_FACTOR_ALREADY_ENABLED` (409) handles attempts to set up or confirm MFA on an already enabled account; weak/same new passwords use `VALIDATION_ERROR`.
- A five-minute proof/challenge/setup is expired at the exact deadline.
- Keep the configured Data Protection key directory when restarting/deploying; the restart test verifies an independently created host can decrypt persisted authenticator state.
